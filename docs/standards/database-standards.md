# Database Standards

**Decision records:** [ADR-0005 SQLAlchemy + Alembic](../adr/0005-database-strategy.md),
[ADR-0006 SQLite and PostgreSQL roles](../adr/0006-sqlite-and-postgresql-roles.md).
**Shared infrastructure:** [WeightsDB](../packages/weightsdb/spec.md).

---

## 1. Ownership

* **One database per application.** `freeweight.sqlite3`, `loadcoach.sqlite3`, `ideapress.sqlite3`
  (or one PostgreSQL database/schema each).
* An application reads and writes **only its own** database. No cross-application queries, no shared
  tables, no "read-only" access to a peer's schema, not even temporarily.
* WeightsDB provides plumbing only — engine, session, pragmas, migrations, backup, health. It defines
  **no** application table and no shared `Base` with domain meaning.
* Each application owns its own `MetaData`, its own models, and its own Alembic history.

---

## 2. Engines

| | SQLite | PostgreSQL |
|---|---|---|
| Role | Default; zero-configuration single-user | Optional; larger, multi-user or long-retention deployments |
| Configured by | Nothing (default path) | `storage.database_url` |
| Pragmas / settings | `foreign_keys=ON`, `journal_mode=WAL`, `busy_timeout=5000`, `synchronous=NORMAL` | `statement_timeout`, `lock_timeout`, application-owned schema |
| Migrations | Auto-applied on startup by default | Applied deliberately (`<app> db upgrade`); auto-migrate defaults to off |
| Concurrency | Single writer; short transactions mandatory | Normal MVCC |

Only these two dialects are supported. Adding a third requires an ADR; the cost of dialect-neutral
SQL is real and is deliberately not paid for MySQL/Oracle/etc.

Rules that keep both working:

* Use SQLAlchemy expression language, not raw SQL, outside migrations.
* **Upserts go through `weightsdb.upsert(...)`**, which emits the dialect's `ON CONFLICT … DO UPDATE`
  against a named unique index. Application code never writes an upsert by hand, and never uses
  select-then-insert, which is a race under both dialects
  ([ADR-0006](../adr/0006-sqlite-and-postgresql-roles.md)). The suite's upserts are: model discovery,
  machine profile, `settings`, `feedback` per `(job_id, source)`, evidence import, and
  `reliability_stats`.
* No dialect-specific column types in models. JSON uses `JSON` (SQLAlchemy renders `JSONB` on
  PostgreSQL via a type decorator in WeightsDB). Timestamps use a timezone-aware type that stores
  UTC and returns aware `datetime` on both dialects.
* No reliance on SQLite's type affinity or on PostgreSQL-only features in application code.
* Integration tests run against **both** dialects in CI for every application and for WeightsDB.

## 3. Schema conventions

* Table names: plural `snake_case` (`benchmark_runs`, `telemetry_samples`).
* Column names: `snake_case`, units in the name (`duration_ms`, `vram_used_bytes`).
* Primary keys: **ULID strings** (26 chars, `CHAR(26)`), generated by BaseAiCore. Time-sortable,
  safe to expose in URLs and logs, no cross-process sequence coordination, no integer-ID enumeration.
  Join tables may use composite keys.
* Foreign keys are declared **and enforced** (`foreign_keys=ON` for SQLite), with an explicit
  `ondelete` on every one: `CASCADE` for owned children (samples under a run), `RESTRICT` for
  references that must not orphan history (a model referenced by results).
* Timestamps: `created_at` on every row; `updated_at` where rows mutate; all timezone-aware UTC.
* Enumerated values are stored as `TEXT` with a `CHECK` constraint, not as native enums — adding a
  value must not require a type migration on PostgreSQL.
* Booleans are real booleans; nullable columns mean something specific and that meaning is documented
  in the model docstring.
* `Unsupported` measurements are stored as `NULL` **plus** a reason column or a reason key in the
  row's JSON detail. `NULL` alone never distinguishes "not measured" from "not measurable". The
  column pair is produced by `weightsdb.measurement_columns(name)`, which yields `<name>` and
  `<name>_unavailable_reason`; a schema that writes a measurement without its reason column is a
  defect, and a naming test asserts the pairing across every application's metadata.
* Large payloads (raw provider responses, exports, generated documents) live in the artifact
  directory; the row stores path, `sha256` and size.

## 4. Indexes

Every query on a page's critical path has an index, and the index exists from the migration that
creates the table — not added later after a slow-page report.

Required at minimum:

* Every foreign key.
* Every column used in a `WHERE`, `ORDER BY` or cursor boundary on a growing table
  (`runs(status, created_at)`, `samples(run_test_id, ordinal)`, `jobs(state, priority, created_at)`,
  `telemetry_samples(run_id, timestamp)`, `events(run_id, sequence)`).
* Unique constraints for natural keys
  (`models(provider_kind, provider_model_name, artifact_digest)`).
* Partial indexes where the dialect supports them and the query is selective
  (`jobs(state) WHERE state IN ('queued','running')`).

Tests assert the query plan for the hot queries (`EXPLAIN QUERY PLAN` on SQLite, `EXPLAIN` on
PostgreSQL) so an accidental full scan on `samples` fails CI rather than a user's dashboard.

## 5. Migrations

* **Alembic**, one linear history per application, from the very first release. Migration `0001`
  creates the initial schema; there is no "the schema is created by the models" mode in any
  environment, including tests.
* Every migration has `upgrade()` and, where technically possible, `downgrade()`. When a downgrade
  would lose data it raises with an explanatory message instead of silently dropping.
* Data migrations are separate revisions from schema migrations, are idempotent, and are batched for
  large tables.
* Migrations are reviewed for lock behaviour on PostgreSQL (no long `ACCESS EXCLUSIVE` on a large
  table without a stated maintenance note).
* SQLite structural changes use Alembic's batch mode.
* **Never** drop and recreate the database as an upgrade path. `--recreate` exists only as an
  explicitly destructive development command, gated behind a confirmation and refused when the
  database is not marked as a development database.

### 5.1 Startup behaviour

```text
current == head              → start
current <  head, SQLite      → back up → upgrade → start   (storage.auto_migrate default true)
current <  head, PostgreSQL  → refuse with MIGRATION_REQUIRED and the exact command (auto off)
current >  head              → refuse: the database was written by a newer version
no alembic_version table     → treat as a new database, stamp and create
```

Migration failure automatically restores the pre-migration backup and reports both the failure and
the restore.

### 5.2 Migration tests (mandatory)

| Test | Asserts |
|---|---|
| Fresh install | Empty DB → head, all tables present, all FKs enforced |
| Stepwise | Every revision applies in order, one at a time |
| Idempotency | Running `upgrade head` twice is a no-op |
| Round trip | `upgrade` then `downgrade` then `upgrade` where downgrade exists |
| Data preservation | Seeded rows survive an upgrade with expected transformations |
| Failure and restore | A deliberately failing migration leaves the original database intact |
| Both dialects | The whole set runs on SQLite and PostgreSQL |
| Model/migration parity | Autogenerate against head produces an empty diff — a model changed without a migration fails CI |
| Upsert concurrency | Two concurrent writers of the same natural key produce one row and no error, on both dialects |

## 6. Transactions and sessions

* Session per unit of work, opened and closed by the service layer, never by domain code.
* Web request: one session, one transaction, committed at the end of a successful request and rolled
  back on any exception.
* Background worker: one session per job/run step, with short transactions. A long benchmark run
  holds **many** short transactions, never one long one.
* SQLite writes use `BEGIN IMMEDIATE` so lock contention fails fast and predictably instead of at
  commit time.
* No nested transactions; use savepoints deliberately and only where a partial failure is
  recoverable.
* Repository methods take a session; they never open one. This is what makes service-level
  transaction boundaries real.
* Bulk inserts (samples, telemetry) are batched (default 100 rows) with an explicit flush cadence,
  and are measured against the budgets in [Performance Targets](../architecture/performance-targets.md) §3.5.

## 7. Backup and restore

```bash
<app> db backup [--output PATH]      # consistent backup (SQLite backup API / pg_dump)
<app> db restore PATH                # refuses to overwrite without --yes; verifies before swapping
<app> db status                      # revision, size, table row counts, integrity check
<app> db vacuum                      # with a preview of the space reclaimed
```

* Automatic backup before every migration and before every destructive bulk operation above a
  configured row threshold.
* **The automatic restore-on-failure guarantee is SQLite-only.** On SQLite, a failed migration
  restores the pre-migration file and the original is byte-identical. On PostgreSQL there is no
  equivalent: `pg_dump`/`pg_restore` is not byte-identical, restoring generally needs privileges the
  application's role deliberately does not hold, and a restore cannot be performed safely underneath a
  live database. PostgreSQL therefore behaves as follows, which is why its `auto_migrate` defaults to
  off: the migration runs inside a transaction where the DDL permits it and rolls back on failure;
  where it does not, the runner reports the exact revision reached, refuses to start, and names the
  backup taken before the attempt and the command to restore it. The difference is stated in
  `MigrationOutcome` and is not papered over.
* Backups are written inside the data root with mode `0600`, named with a UTC timestamp and the
  schema revision, and are never sent anywhere.
* Retention is configurable (default: keep the last 5 automatic backups); rotation is logged.
* Restore verifies the backup opens, is at a known revision, and passes an integrity check before
  replacing anything; the previous file is retained as `.pre-restore` until the new one opens cleanly.
* A restore test exists in every application's suite.

## 8. Destructive operations

* Always preview: "this will delete 412 samples, 3 runs, 0 models".
* Always confirm: `--yes` in the CLI, typed confirmation in the UI.
* Always transactional, with an automatic backup above the threshold.
* Deleting results never deletes model or machine rows — history of *what exists* outlives history of
  *what was measured*.
* Cascades are declared and tested; a cascade that would remove more than the preview stated is a
  defect.

---

## 9. Health

`GET /api/v1/health` and `<app> health` include a `database` component reporting: dialect and
version, current revision vs head, WAL/journal mode, file size, free space on the containing device,
last backup age, and integrity-check status. Degraded conditions: pending migration, low disk,
integrity warning, backup older than the configured expectation.

## 10. Anti-patterns

| Banned | Why |
|---|---|
| `CREATE TABLE IF NOT EXISTS` at connect time | Not a migration system; drifts silently across versions |
| Dropping the database to upgrade | Requirement §15 forbids it; users have irreplaceable measurement history |
| Cross-application queries | Binds a reader to a writer's internal schema |
| Storing measurements as `0` when unavailable | Fabricates data ([ADR-0016](../adr/0016-unavailable-is-not-zero.md)) |
| ORM objects escaping the repository layer | Lazy loads outside a session, and domain code coupled to SQLAlchemy |
| String-built SQL | Injection risk and dialect breakage |
| One long transaction for a whole run | Blocks readers, loses everything on a crash |
| Naive datetimes | Ambiguous history, broken comparisons |
| Integer primary keys exposed in URLs | Enumerable, and awkward to merge across machines |
